# Balans: запуск для портфолио

## Зачем это всё

Продукт Balans готов (этапы 0–9). Теперь он становится **витриной разработчика Даниэла**. Сайт будут открывать HR, руководители, тимлиды и CTO, заказчики с Upwork. Они оценивают не автомойку, а то, что умеет автор: вкус, скорость, аккуратность, работу на телефоне, чистый код.

Срок жёсткий: сайт должен быть в резюме во вторник. Поэтому после каждой фазы сайт остаётся рабочим, а всё необязательное уходит в список «после запуска».

Работа разбита на 4 запуска: `docs/launch/RUN_1…RUN_4`. Каждый запуск — отдельная сессия. Состояние между сессиями живёт в `docs/launch/PROGRESS.md`.

## Что нельзя сломать

- Вход по email и через Google, выход, сброс пароля, приглашение, демо. Это проверяется после каждой фазы, которая трогает `src/proxy.ts`, layout или маршруты.
- Права в базе (RLS). Политики не трогаем. Новые миграции только те, что названы в RUN-файле.
- Дизайн-систему: `docs/DESIGN.md` и токены. Основной текст 16 px, цели на телефоне не меньше 44 px, 6 ширин (360, 390, 768, 1024, 1440, 1920), обе темы.
- Боевой сайт. Работаем в ветке `launch/run-N`, пушим её, Vercel даёт preview-ссылку. В `main` вливаем только после «ок» Даниэла в конце запуска.

## Какой инструмент для чего

Перед фазой загрузи нужные skills. Если инструмента нет, скажи об этом в отчёте и работай по официальной документации через context7, а не по памяти.

| Задача | Инструмент |
|---|---|
| Актуальная документация (next-intl, Next 16, R3F, drei, Supabase) | **context7** (MCP). API библиотек не писать по памяти |
| Вид и вёрстка лендинга | **frontend-design** (Anthropic) + **impeccable** (уже в проекте) + `docs/DESIGN.md` |
| 3D-сцена | skills **threejs-react-three-fiber**, **threejs-performance**, **threejs-geometry**, **threejs-materials**, **threejs-lighting** (CloudAI-X/threejs-skills) |
| Анимации при прокрутке | **gsap-scrolltrigger**, **gsap-react**, **gsap-performance** (GreenSock) |
| Правила скорости React/Next | **react-best-practices** (Vercel) |
| Замер скорости, Core Web Vitals, доступность, SEO | **web-quality-skills** (performance, core-web-vitals, accessibility, seo, web-quality-audit) + **Chrome DevTools MCP** + агент **perf-auditor** |
| Скриншоты 6 ширин | skill **check-screens** (уже в проекте) + агент **screen-reviewer** |

Как их соединять: документация (context7) → код по профильному skill → `check-screens` → `perf-auditor` → исправления по его отчёту → повторный замер. Замер всегда «до» и «после», в одинаковых условиях.

## Ворота качества (после каждой фазы)

Фаза закрыта, только когда всё ниже выполнено и есть доказательство (вывод команды, скриншот, цифра):

1. `npm run build`, `npm run lint`, `npx tsc --noEmit` без ошибок.
2. В консоли браузера на затронутых страницах нет ошибок и hydration warning.
3. `check-screens` на затронутых страницах: 6 ширин × 2 темы × 2 языка (после RUN 1). Нет горизонтальной прокрутки. Скриншоты посмотреть глазами через `screen-reviewer`, а не только «скрипт прошёл».
4. Если трогали proxy, layout, маршруты или auth: сценарий «вход по email → кабинет → выход → закрытая страница не открывается → демо открывается» проходит в браузере.
5. Если трогали лендинг или 3D: отчёт `perf-auditor`, бюджет скорости выполнен.
6. Коммит с понятным сообщением. Строка в `docs/launch/PROGRESS.md`: что сделано, что проверено, цифры.

Нельзя: отключать или пропускать проверку, чтобы пройти ворота; писать «готово» без доказательства; чинить симптом заглушкой.

## Бюджет скорости (лендинг, телефон)

| Показатель | Цель |
|---|---|
| Lighthouse Performance (mobile, `npx lighthouse`) | ≥ 90 |
| LCP | ≤ 2,5 с |
| CLS | ≤ 0,1 |
| INP / TBT | ≤ 200 мс |
| JS 3D-сцены | отдельный чанк, грузится после показа страницы, не входит в первый экран |

Chrome DevTools MCP: `lighthouse_audit` не считает категорию Performance. Оценку Performance бери из `npx lighthouse <url> --form-factor=mobile --output=json`, причины ищи через `performance_start_trace` и `performance_analyze_insight`.

## Самостоятельность и остановки

- Работай сам от фазы к фазе. Не спрашивай то, что можно решить по ТЗ, `DESIGN.md` и этому файлу. Принятые решения записывай в `PROGRESS.md` в раздел «Решения».
- Останавливайся только в точках **СТОП**, названных в RUN-файле, и в двух случаях: одна и та же проблема не решилась за 2 попытки; нужно действие, которое может сделать только Даниэл (панель Supabase, SQL Editor, его телефон).
- Формат сообщения на СТОП:
  1. Что сделано (3–6 строк простыми словами).
  2. Доказательства: цифры, preview-ссылка, пути к скриншотам.
  3. **Что сделать Даниэлу**: пронумерованные шаги, куда нажать.
  4. Что будет после его ответа.
- Идеи сверх задачи не делай. Записывай в `PROGRESS.md` в раздел «После запуска».
- Объясняй простыми словами. Незнакомый термин — одна фраза пояснения. Даниэл будет рассказывать об этом на собеседовании.

## Правила 3D (коротко, подробности в RUN_3)

- Сначала всегда видна картинка (poster). 3D подгружается после загрузки страницы и плавно заменяет её. LCP — это текст или картинка, никогда не canvas.
- Сцена из простых фигур кодом (без тяжёлых моделей и текстур). Цвета из токенов темы, реагирует на смену темы.
- Не рисуем кадры, когда сцена за экраном или вкладка скрыта.
- Ступени качества по FPS. Запасной вариант (остаётся картинка): «уменьшить движение», нет WebGL, режим экономии трафика, слабое устройство, потеря контекста.
- Canvas не мешает прокрутке пальцем, скрыт от экранного диктора.
- Выключатель: `NEXT_PUBLIC_HERO_3D=off` оставляет только картинку.

## Решения

(что решено по ходу и почему, одной строкой)

### RUN 1, план (фаза 0, 2026-11-15)

1. Основа: `next-intl` 4.15, `src/i18n/` (список языков, определение языка, запрос), `messages/ru.json` и `messages/en.json`, провайдер в корневом layout, `?lang=` в `src/proxy.ts`, переключатель RU / EN, `formatSom` / даты / месяцы с языком.
2. Гостевые страницы → 3. кабинет → 4. ошибки аудита → 5. миграция `0009` и письма → СТОП A → 6. проверка всего → СТОП B.

- **Язык из cookie и `cacheComponents`.** В проекте включён `cacheComponents`: Next заранее собирает «каркас» страницы, а язык из cookie известен только в момент запроса. По документации Next 16 (`generate-viewport.md`, `migrating-to-cache-components.md`) весь документ обёрнут в `<Suspense>` в корневом layout: страница целиком собирается на сервере при запросе. Цена: у страниц нет заранее готового каркаса с текстом. Статичный каркас на каждый язык возможен только с адресами `/ru` и `/en` (уже в «После запуска»).
- **Имя cookie:** `lang` (значения `ru`, `en`, год). Тот же ключ, что в ссылке `?lang=en`.
- **Язык браузера:** идём по списку `Accept-Language` по приоритету; первый из `ru`/`ky` даёт `ru`, первый `en` даёт `en`, ничего не подошло — `en`.
- **Даты:** русский остаётся `04.11.2026` (дизайн не меняем), английский `Nov 4, 2026` (форма `11/04/2026` читается двояко).
- **SQL-функции** уже возвращают коды ошибок (`errcode`), русского текста в них нет: менять нечего, тексты берутся из словарей по коду.

### RUN 1, по ходу работы

- **Ключи словарей по страницам** (`auth`, `dashboard`, `operations`, …) и общий `common`. TypeScript проверяет ключи: опечатка в `t("…")` ломает сборку. Схемы Zod (форма записи, настройки) стали функциями от `t`: одна схема по-прежнему проверяет и в браузере, и на сервере, но ошибки на языке посетителя.
- **Переключатель RU / EN** показывает язык, на который переключит (`EN` на русском сайте). Он вызывает серверное действие, которое ставит cookie; Next сам перерисовывает страницу — вход не теряется (проверено).
- **Русские формы множественного числа** через ICU в словаре (`{count, plural, one {# участник} few {# участника} many {# участников}}`), пример — счётчик участников в «Команде».
- **Календарь:** неделя с понедельника на обоих языках (бизнес в Бишкеке).
- **`/admin` и `/design`** остаются на русском, но общие компоненты на них (меню, переключатель темы) идут за выбранным языком.
- **Манифест PWA** остался статичным и на русском: браузер кеширует его один раз, язык из cookie там не прочитать без лишней динамики.
- **`global-error`** заменяет корневой layout и живёт без провайдера переводов: язык берёт из cookie в браузере, тексты из тех же словарей.
- **Пакет `cn` не удалён:** аудит назвал его неиспользуемым, но это движок `cn()` от shadcn (замена `clsx` + `tailwind-merge`, `src/lib/utils.ts`). После удаления `tsc` упал — вернул.
- **Наведение кнопок:** `secondary` и `destructive` теперь через токены `secondary-hover`, `destructive-hover` (было `color-mix` и `/90` прямо в классе).
- **Границы светлой темы:** `--border` 0.915 → 0.87 (1.3 → 1.5:1 на белом), `--input` 0.66 → 0.60 (3.1 → 3.95:1). Тёмная тема без изменений. Обоснование в `DESIGN.md` §3.
- **`check-screens --lang`:** по умолчанию снимает оба языка (24 снимка на страницу), имя файла `<страница>-<язык>-<тема>-<ширина>.png`.
- **Миграция `0009_locale.sql`:** `create_business` и `create_demo_business` получили аргумент языка со значением по умолчанию `ru`, поэтому старые вызовы без него продолжают работать. Если демо-гость сменил язык и снова нажал «Посмотреть демо», база заменяет его демо на демо нового языка.

### RUN 2, по ходу работы

- **Подпись в главном блоке без родительного падежа** («Pet-проект · Даниэл Кубанычбеков»): окончание «-ва» у фамилии в Кыргызстане читается как женская форма (решение Даниэла).
- **Резюме лежит под постоянными именами:** `public/resume/Daniel-Kubanychbekov-CV-ru.pdf` и `…-CV-en.pdf`. Кнопка выбирает файл по языку сайта. Чтобы обновить резюме, достаточно заменить файл с тем же именем. Пока английский файл — копия русского, Даниэл заменит его сам.

- **Тёмная тема гостевых страниц** через `forcedTheme` в `ThemeProvider` по адресу: темой управляют только кабинет, `/admin` и `/design`, всё остальное (включая 404 и ошибки) тёмное. Скрипт `next-themes` получает адрес ещё на сервере и ставит `dark` до первой отрисовки (проверено: класс `dark` есть до гидратации при светлой системной теме). Переход из демо в кабинет возвращает тему пользователя.
- **Анимации на CSS, а не GSAP** (отступление от черновика `LANDING.md`): появление и выпрямление при прокрутке делает сам браузер (`animation-timeline: view()`), 0 КБ JavaScript. Где поддержки нет (Firefox) — блоки просто видны. Подробно в `DESIGN.md` §13.
- **`check-screens` снимает с «уменьшить движение»:** иначе блоки с появлением при прокрутке ниже первого экрана на снимке всей страницы прозрачные.
- **Данные витрины фиксированные** (`app/_landing/sample-data.ts`) в пределах того, что даёт демо-сид, месяцы и даты — от сегодняшнего дня в Бишкеке. Картинка главного блока и окно кабинета показывают одни и те же цифры.
- **Линия прибыли на картинке** поднята на величину наклона изометрии: иначе растущая прибыль выглядела падающей.
- **Окно кабинета `inert`:** ничего внутри не нажимается и не получает фокус; ссылки меню без предзагрузки (`Sidebar prefetch={false}`), чтобы лендинг не грузил страницы кабинета. График (recharts) грузится, когда окно в пределах экрана от видимой области.
- **Поле даты в витрине формы — `Input` только для чтения, а не `DatePicker`:** календарь (react-day-picker, date-fns) и zod через `lib/entry.ts` грузились бы с лендингом ради окна, которое там не открывается. Внешне поле то же. Кабинет не тронут.
- **График грузится за 200 px до появления** (было «за экран»): на телефоне прежняя зона захватывала его с первого кадра, +100 КБ JS и ~1 с TBT (замер `perf-auditor`).
- **Кнопка RU/EN:** доступное имя начинается с видимого текста («EN: переключить на английский…») — требование Lighthouse `label-content-name-mismatch`.
- **Бюджет скорости в RUN 2 не добит (решение Даниэла 2026-11-16):** Lighthouse mobile 77 / 75 (расчётный TBT ~1,1–1,3 с; с реальным замедлением CPU 90 / 88), LCP ~1 с, CLS 0. Принято как точка отсчёта для RUN 3, окончательный замер на Vercel в RUN 4. Невыполненные идеи — в «После запуска».
- **Лендинг рендерится на каждый запрос** (`await connection()`): данные датированы сегодняшним днём. Он и так был динамическим из-за языка в cookie.
